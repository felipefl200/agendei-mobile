Resumo executivo

O projeto tem uma base melhor do que a média de MVPs mobile: há separação entre domain, application/useCases, infra, features e components, além de navegação com Expo Router, cache com TanStack Query e persistência de token com SecureStore. Isso coloca o código mais perto de um híbrido entre Clean Architecture leve e módulos por feature com MVVM do que de um app “flat”.

Os gargalos principais hoje não estão no core arquitetural, mas em governança e acabamento técnico: a suíte de testes está quebrada na execução real, não há CI/CD visível no repositório, a proteção de rotas ainda é parcial apesar de o SDK já suportar Stack.Protected e a validação de entrada depende mais do backend do que de contratos explícitos no app.[1][7]

Síntese

Recomendação central: preservar a arquitetura atual e investir em quatro frentes incrementais de alto retorno e baixo risco: proteger rotas de forma declarativa, estabilizar os testes, formalizar contratos de validação e endurecer fronteiras entre features.

Contexto auditado

O projeto auditado não usa Next.js nem shadcn/ui; a stack real encontrada no repositório é mobile. A navegação parte de expo-router/entry, as rotas ficam em src/app, a UI usa React Native puro com componentes próprios, e a integração com backend é REST via ky e adapters em src/infra/adapters.

Core protegido

Antes de recomendar mudanças, há quatro decisões já corretas e consistentes que devem ser preservadas. A primeira é a base Expo/React Native com Expo Router, que combina bem com apps de produto mobile e já suporta rotas protegidas declarativas no SDK atual.[1]

A segunda é a divisão em domain, application, infra e features, porque ela reduz acoplamento entre UI, contratos e acesso HTTP. A terceira é o uso de TanStack Query para server state e Zustand apenas para sessão, o que está alinhado com o benchmark de arquitetura modular e com o papel recomendado para cache e estado remoto.[4][8]

A quarta é o armazenamento de token em SecureStore, apropriado para segredos curtos como credenciais e tokens. As sugestões abaixo não pressupõem trocar Expo Router, TanStack Query, SecureStore, feature folders ou a separação em use cases/adapters.[3]

Dependências e versionamento

Status atual: o conjunto principal está coerente e atualizado para a linha Expo 56, sem indícios fortes de pacotes abandonados no núcleo. Os itens desatualizados levantados pelo npm outdated são majoritariamente patches e minors de baixo risco, com uma exceção importante: react-native 0.86.0 já existe, mas a adoção deve seguir a janela de compatibilidade do Expo SDK e não deve ser tratada como upgrade isolado.

Alinhamento com o mercado: usar EXPO_PUBLIC_* para configuração de API está em linha com a documentação do Expo, e expo-secure-store é uma escolha adequada para tokens. Também é positivo ver TanStack Query com staleTime explícito, já que o default do framework considera os dados “stale” imediatamente.[2][3][4]

Prioridade Item Problema Solução sugerida Referência
🔴 Alta Configuração dupla de testes O projeto roda Vitest, mas mantém jest.config.js e @types/jest sem uso comprovado. Isso confunde tooling, onboarding e manutenção. Escolher um runner como fonte única de verdade. Como a suíte atual já usa Vitest, remover a configuração residual de Jest ou rebaixá-la a legado documentado. Vitest coverage guide[7]
🟡 Média Atualizações patch/minor expo, expo-router, prettier, vitest e alguns pacotes RN têm atualização disponível. Agrupar patches em um único PR mensal com smoke test em Android e web. Não atualizar react-native fora da matriz suportada pelo Expo SDK. Ignite como benchmark de base estável de stack[10]
🟡 Média Configuração de SecureStore O uso do pacote está correto, mas app.json não declara o plugin do expo-secure-store. Isso deixa de explicitar backup/Face ID para builds nativos. Adicionar o plugin do SecureStore no app.json, mesmo sem usar biometria agora, para deixar o comportamento de backup e permissões explícito. Expo SecureStore docs[3]
🟢 Baixa Dependências redundantes Não há duplicação grave de libs de estado, data ou forms. A redundância prática está mais em arquivos/configuração do que em runtime. Manter TanStack Query + Zustand e cortar apenas artefatos residuais como config de Jest sem uso. bulletproof-react project structure[8]

Arquitetura de componentes

Status atual: a metodologia observada é um híbrido de módulos por feature com MVVM. As telas em src/features/*/screens delegam parte importante da lógica para hooks de view-model, e o repositório documenta explicitamente esse objetivo no backlog de migração para MVVM.

Alinhamento com o mercado: isso conversa bem com a recomendação de concentrar a maior parte do código dentro de features e preservar fluxo unidirecional entre camadas, como em bulletproof-react e Feature-Sliced Design. O projeto já está melhor do que a média ao manter app apenas como casca de rota e deixar a UI concreta nos módulos.[8][9]

Prioridade Item Problema Solução sugerida Referência
🔴 Alta Proteção de rotas Hoje apenas src/app/index.tsx redireciona com base em autenticação. As tabs e demais rotas não estão protegidas declarativamente no layout. Introduzir grupos de rota autenticados e usar Stack.Protected ou Tabs.Protected no layout principal, com fallback claro durante isRestoring. Expo Router protected routes[1]
🟡 Média Fronteiras entre features Há dependências cruzadas como booking importando hooks de features/shared. Isso ainda funciona, mas sem regra de importação pode crescer para acoplamento lateral. Adicionar restrições de import por ESLint e preferir composição via camada de app ou APIs públicas de feature. bulletproof-react unidirectional flow[8]
FSD import rule[9]
🟡 Média Responsabilidade do ViewModel Os view-models estão no caminho certo, mas ainda carregam console.warn/console.error de depuração e algumas regras de UI embutidas. Remover logs de desenvolvimento do runtime e separar melhor mapeamento de mensagem, analytics e side-effects em helpers ou serviços. Ignite como benchmark de base madura com observabilidade estruturada[10]
🟢 Baixa Colocation de componentes Componentes feature-specific ainda vivem em src/components por tipo de tela, não por domínio. Sem reescrever tudo, mover gradualmente componentes muito específicos para dentro de cada feature quando forem tocados em manutenção futura. bulletproof-react feature folders[8]

Sistema de tema e design tokens

Status atual: o arquivo src/constants/theme.ts centraliza cores, espaçamentos, raios, sombras e tamanhos. Isso é um ponto forte: já existe uma camada de tokens de design reutilizáveis em vez de estilos completamente arbitrários espalhados pela base.

Alinhamento com o mercado: a existência de tokens centralizados se aproxima de starter kits maduros como Ignite, que tratam tema como infraestrutura, não como detalhe local de componente. O projeto, porém, ainda está em um estágio monolítico de tema: modo claro fixo em app.json, sem semantic tokens dinâmicos e sem estratégia explícita para dark mode.

Prioridade Item Problema Solução sugerida Referência
🟡 Média Dark mode userInterfaceStyle está fixo em light, o que limita evolução de produto e acessibilidade visual. Introduzir tokens semânticos por papel de UI e um tema alternativo escuro antes de qualquer redesign visual mais amplo. Ignite benchmark com suporte de theming[10]
🟡 Média Escala tipográfica Há tamanhos centralizados, mas falta um contrato mais claro de uso por contexto: título, subtítulo, legenda, corpo, rótulo. Criar um mapa semântico como TYPOGRAPHY.headingLg, bodyMd, captionSm para reduzir arbitrariedade futura. Prática comum em design systems e boilerplates maduros como Ignite[10]
🟢 Baixa Tokens redundantes O tema mistura tokens semânticos e nomes genéricos como gray1 a gray5, o que dificulta consistência de intenção. Deprecar gradualmente tokens genéricos e preferir nomes por papel: textMuted, surfaceSoft, borderSoft. Feature-Sliced recomenda segmentos e nomes por propósito, não por essência[9]
🟢 Baixa Fonte e branding O app funciona bem com fontes do sistema, mas não possui estratégia de branding tipográfico consistente. Só introduzir expo-font quando houver ganho real de marca; não é prioridade funcional agora. Ignite stack inclui suporte a fontes como infraestrutura opcional[10]

Estrutura e organização de pastas

Status atual: a estrutura é intuitiva e escalável para o estágio do produto. O eixo principal está em src/features, enquanto src/app funciona como casca de roteamento, exatamente como se espera em arquiteturas modulares modernas.[8]

Alinhamento com o mercado: o projeto já converge com a ideia de separar código por domínio de negócio e responsabilidade técnica. O principal desvio em relação a benchmarks como Feature-Sliced é o uso de segmentos muito genéricos em shared e a ausência de APIs públicas explícitas por módulo.[8][9]

Prioridade Item Problema Solução sugerida Referência
🟡 Média APIs públicas de módulo As features não expõem contratos públicos claros; imports internos podem se espalhar com o tempo. Criar pontos de entrada mínimos por feature ou por segmento realmente compartilhado, sem voltar a um uso indiscriminado de barrel files. FSD public API e slices[9]
bulletproof-react evita barrels amplos[8]
🟡 Média Documentação arquitetural O backlog pede ARCHITECTURE.md, mas o arquivo ainda não existe. Isso aumenta custo de onboarding. Adicionar um documento curto com regras de dependência, exemplo de fluxo rota → screen → view-model → use case → adapter. FSD enfatiza semântica das camadas e áreas de foco documentadas[9]
🟢 Baixa Colocation de testes Os testes dos view-models já estão próximos ao código, o que é positivo, mas só isso está co-localizado. Manter a estratégia de proximidade e ampliar para hooks críticos e utils que concentram regra de negócio. bulletproof-react feature-local code[8]
🟢 Baixa Nomenclatura de segmentos components, types e utils continuam sendo nomes utilitários amplos. Sem reestruturar o repo todo, adotar nomes por finalidade nos novos módulos: ui, api, model, config. FSD layers and segments[9]

Performance e DX

Status atual: a experiência de desenvolvimento é boa no básico: lint está funcional, alias de import está configurado e o cache remoto usa TanStack Query com staleTime de 1 minuto. Também é positivo que mutações importantes invalidem queries relacionadas, como criação e cancelamento de consultas.[4]

Alinhamento com o mercado: o projeto já internalizou a ideia de cache de server state, mas ainda há ganhos simples em listas, loading states e observabilidade. A documentação do React Native reforça que ScrollView renderiza todos os filhos de uma vez, enquanto FlatList faz renderização preguiçosa; hoje o app usa ScrollView em todas as telas principais, inclusive as de listagem.[5]

Prioridade Item Problema Solução sugerida Referência
🔴 Alta Listas com ScrollView AppointmentsScreen, SearchDoctorScreen e DashboardScreen renderizam coleções em ScrollView. Isso é aceitável no MVP, mas não escala bem. Migrar listas de dados para FlatList e manter ScrollView apenas para conteúdo curto e majoritariamente estático. React Native ScrollView docs[5]
🟡 Média Feedback de carregamento Há mensagens textuais de loading, mas quase nenhum estado intermediário estruturado, skeleton ou placeholders por bloco. Criar componentes simples de skeleton para cards e listas. Isso melhora UX sem alterar arquitetura. Prática comum em produtos mobile maduros; Ignite traz componentes e patterns para evolução incremental[10]
🟡 Média Logs em produção Há múltiplos console.warn e console.error em login, cadastro e cliente HTTP. Isso polui debugging e telemetria. Substituir por logger central com níveis por ambiente e possibilidade de integração futura com observabilidade. Base madura de produto tende a separar logging operacional de console ad hoc[10]
🟢 Baixa Configuração de cache O staleTime global de 1 minuto já evita parte do refetch excessivo, mas não há estratégia diferenciada por recurso. Ajustar por domínio: especialidades podem ter staleTime longo; disponibilidade médica deve ser mais curta e talvez sensível a foco. TanStack important defaults[4]

Segurança e tipagem

Status atual: o projeto já usa strict: true, o que é um bom sinal de maturidade. Há pouco uso de cast inseguro, mas existem pontos específicos como input as GetDoctorAvailabilityInput e parsing otimista de erro HTTP que merecem endurecimento.[6]

Alinhamento com o mercado: é correto armazenar o token em SecureStore e usar EXPO_PUBLIC_API_URL em vez de hacks de config. O problema está menos na ferramenta e mais na falta de contratos explícitos: o app não usa zod nem validações locais de payload/resposta, apesar de a própria documentação da API já descrever formatos de erro e campos opcionais com bastante detalhe.[2][3]

Prioridade Item Problema Solução sugerida Referência
🔴 Alta Validação de contratos Requisições e respostas REST são aceitas quase diretamente nos adapters. Isso aumenta risco de falha silenciosa quando o backend muda. Adicionar schemas de entrada/saída por endpoint crítico e parsear no adapter, começando por auth, doctors e appointments. TypeScript strict dá garantias melhores quando combinado com contratos reais[6]
🔴 Alta Auth sem guarda central Mesmo com estado de sessão em store, as rotas não estão protegidas no layout. Segurança de navegação depende de redirects pontuais. Aplicar proteção declarativa no roteador e manter checagem de autorização no backend como fonte final de verdade. Expo Router protected routes[1]
🟡 Média Uso de variáveis de ambiente O uso atual está correto, mas o projeto não separa claramente ambientes locais, staging e produção. Adotar .env.local para desenvolvimento, padronizar valores por ambiente e documentar o fluxo. Nunca colocar segredos em EXPO_PUBLIC_*. Expo environment variables[2]
🟡 Média Tratamento de erros O cliente HTTP tenta interpretar erro JSON, mas não valida shape e faz cast parcial. Adicionar type guard ou schema para AppErrorPayload antes de construir AppError. TypeScript strict[6]

Cobertura de testes

Status atual: a estratégia declarada é unitária para view-models usando Testing Library e Vitest. Na prática, a base tem apenas 3 arquivos de teste e a execução real falha antes mesmo de rodar os casos: vitest run retorna 3 suítes quebradas, 0 testes executados e erro de parsing Unexpected token 'typeof'.

Alinhamento com o mercado: a intenção de testar hooks/view-models perto do domínio está correta. O desvio é de confiabilidade operacional: sem suíte verde, sem cobertura e sem CI, o valor dos testes cai drasticamente, apesar de o próprio Vitest oferecer um caminho direto para ativar cobertura com provider v8 ou istanbul.[7]

Prioridade Item Problema Solução sugerida Referência
🔴 Alta Suíte quebrada Os testes existem, mas hoje não passam nem como “smoke test”. Isso invalida o papel deles como rede de segurança. Fazer um PR exclusivo para estabilização: alinhar extensão dos testes, transformação de JSX/TSX e mocks de RN/Expo até obter suíte verde. Vitest coverage/setup[7]
🔴 Alta Ausência de CI Sem workflow de PR, regressões passam despercebidas e os testes podem apodrecer novamente. Adicionar pipeline mínimo com npm ci, npm run lint e npm test em cada PR. Ignite usa infraestrutura de automação e testes como base, não como etapa tardia[10]
🟡 Média Cobertura inexistente Não há script de coverage nem critérios mínimos por módulo. Adicionar "coverage": "vitest run --coverage" e incluir src/**/*.{ts,tsx} em coverage.include. Vitest coverage guide[7]
🟡 Média Escopo limitado Não há testes de adapters, contratos HTTP ou jornadas críticas como login, busca de médico e agendamento. Expandir em três níveis: view-models críticos, adapters com mocks de payload e um pequeno conjunto e2e futuramente. Ignite inclui Jest e Maestro como referência de maturidade móvel[10]

Prioridades sugeridas

Sem mexer no core protegido, a ordem de maior retorno é esta. Primeiro, fechar as rotas autenticadas no layout e restaurar a suíte de testes. Depois, formalizar contratos de API e endurecer as fronteiras entre features. Por fim, evoluir tema, dark mode e ergonomia visual.

Componente representativo

function SearchDoctorScreen() {
  const vm = useSearchDoctorViewModel()

  return (
    <SafeAreaView edges={['top']} style={styles.safeArea}>
      <View style={styles.container}>
        <ScrollView contentContainerStyle={styles.content}>
          <Input onChangeText={vm.setQuery} value={vm.query} />
          {vm.specialties.map((specialty) => (
            <FilterChip
              key={specialty.id ?? 'all'}
              active={specialty.active}
              label={specialty.label}
              onPress={() => vm.handleSelectSpecialty(specialty.id)}
            />
          ))}
          {vm.doctors.map((doctor) => (
            <DoctorCard
              key={doctor.id}
              name={doctor.name}
              specialty={doctor.specialty}
              onPress={() => vm.handleSelectDoctor(doctor.id)}
            />
          ))}
        </ScrollView>
      </View>
    </SafeAreaView>
  )
}

  const isAuthenticated = useAuthStore((state) => state.isAuthenticated)
  const isRestoring = useAuthStore((state) => state.isRestoring)

  if (isRestoring) {
    return null
  }

    return <Redirect href="/dashboard" />
  }

  return <LoginScreen />
